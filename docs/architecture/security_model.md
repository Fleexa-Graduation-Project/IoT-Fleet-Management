# Security Model

Security in Fleexa is implemented natively at every layer rather than bolted on: device identity is enforced by AWS IoT Core itself, user identity by Amazon Cognito, service permissions by per-Lambda IAM roles generated from Terraform, and data isolation by convention enforced in every table key and every MQTT topic. This document summarizes each layer as it is actually implemented in this codebase; see [`system_architecture.md`](./system_architecture.md) for where each piece sits, and [`data_flow.md`](./data_flow.md) for how a request or message actually flows through them.

---

## 1. Device identity — mutual TLS + IoT Policies

Every simulated (and, in principle, physical) device authenticates to AWS IoT Core using an X.509 certificate and mutual TLS — there are no shared secrets or API keys for device connectivity. Certificates live under `devices/certs/` and are excluded from version control expectations for real deployments; the IoT infrastructure itself is provisioned by the `iot_core` Terraform module (`infra-iot-fleet/terraform/modules/iot_core/main.tf`):

- An `aws_iot_thing_type` classifies devices (`deviceType`, `location`, `version` as searchable attributes).
- An `aws_iot_policy` (`device_policy`) is the actual authorization boundary. It grants a connecting device, scoped by its own `ThingName` (`${iot:Connection.Thing.ThingName}`):
  - `iot:Connect` only as its own client ID.
  - `iot:Publish` only on `devices/*/{ThingName}/telemetry` and `devices/*/{ThingName}/alerts`.
  - `iot:Subscribe` / `iot:Receive` only on `devices/*/{ThingName}/commands`.

Because the policy variable is the device's own certificate-bound `ThingName`, a device physically cannot publish telemetry as another device, subscribe to another device's commands, or receive commands not addressed to it — this is enforced by IoT Core itself, before any message ever reaches application code.

## 2. Message-level validation

Even though the IoT Policy constrains *which* topics a device can touch, every message that does arrive is still independently validated in `backend/internal/validation/validator.go` before it is trusted:
- The topic must match `devices/{user_id}/{device_id}/{telemetry|alerts}` exactly (`validateTopic`).
- The envelope's `device_id` must match the topic's device segment (`validateEnvelope`) — this stops a message from silently attributing data to a different device than the topic implies.
- `user_id` and `type` must be present, the payload must be non-empty, and the timestamp cannot be more than 60 seconds in the future.
- The payload is checked against the device-type-specific rules registered in `internal/devices`, mirroring the JSON Schemas documented under `backend/docs/mqtt/schemas/`.

## 3. User identity — Amazon Cognito + JWT

Mobile/web clients never talk to AWS directly and never hold long-lived AWS credentials. Authentication is delegated entirely to an **Amazon Cognito User Pool** (`infra-iot-fleet/terraform/modules/cognito`):
- Sign-up, sign-in, password reset, and account changes are all proxied by `api-service` through `internal/auth/cognito.go`, which calls the Cognito API (`SignUp`, `InitiateAuth`, `ForgotPassword`, etc.) — the backend never stores a password itself.
- The Cognito User Pool enforces an 8-character-minimum password policy requiring upper/lowercase, numbers, and symbols, and issues short-lived tokens: access/ID tokens valid for 60 minutes, refresh tokens for 30 days.

Every protected REST route is guarded by `internal/auth.Middleware()`:
- Requires a `Bearer` JWT in the `Authorization` header.
- Verifies the token's signature against Cognito's public JWKS, fetched once at cold start and cached in-process (`InitJWKS`, refreshed hourly) — so authorization never costs a network round trip to Cognito per request.
- Explicitly requires `token_use == "access"`, rejecting ID tokens presented as bearer tokens.
- Extracts `user_id` from the token's `sub` claim and stores it in the Gin request context; every downstream handler reads `user_id` from there rather than trusting any client-supplied identifier.

API Gateway itself is a plain HTTP API (`AWS_PROXY` integration to a single Lambda) — Cognito enforcement happens inside `api-service`'s own Gin middleware rather than as an API Gateway Cognito Authorizer resource, but the effect (no unauthenticated access to protected routes) is the same.

## 4. Cloud infrastructure — least-privilege IAM per Lambda

Every Lambda has its own dedicated IAM execution role, generated by Terraform, scoped only to what that specific function needs:

| Function | IAM role (Terraform) | Granted actions |
| :--- | :--- | :--- |
| `api-service` | `api_lambda_role` (module `api_gateway`) | DynamoDB CRUD (`PutItem`/`GetItem`/`UpdateItem`/`Query`/`Scan`/`DeleteItem`), `iot:Publish`/`iot:Connect` (to dispatch commands), `s3:GetObject` (cold-tier chart reads), and the specific Cognito IdP actions needed for auth (`SignUp`, `InitiateAuth`, `ForgotPassword`, `ChangePassword`, `GetUser`, `DeleteUser`, etc.). |
| `iot-ingestion`, `door-watch`, `ac-timer-watch` | shared `lambda` module role, via `iot_ingestion_policy` | DynamoDB read/write actions, plus `iot:Publish`/`iot:Connect` (needed by `ac-timer-watch` to send OFF commands, and reused by the other two functions from the same policy document). |
| `daily_aggregator` (Python cron) | `aggregator_lambda_role` (module `cron_aggregator`) | DynamoDB `Scan`/`Query`/`GetItem` (read-only), and `s3:PutObject`/`GetObject`/`ListBucket` scoped to the data-lake bucket ARN specifically. |
| `db-export` | `export_lambda_role` (module `cron_export`) | DynamoDB `Scan` (read-only) and `s3:PutObject` scoped to the data-lake bucket ARN. |

Every role also attaches the AWS-managed `AWSLambdaBasicExecutionRole` policy for CloudWatch Logs, and nothing more. Note that current DynamoDB actions are granted with `Resource = "*"` rather than pinned to individual table ARNs — the isolation between tenants is therefore enforced at the application layer (every query is scoped by `user_id`/`user_device_id`, see below), not by IAM resource conditions; the S3 and Cognito grants, by contrast, are already scoped to specific resource ARNs/actions.

## 5. Per-user data isolation

Every DynamoDB table and every MQTT topic carries the owning user's ID, so a query or a message can never cross accounts:

| Table | Partition key | Sort key |
| :--- | :--- | :--- |
| `Fleexa_Devices` | `user_id` | `device_id` |
| `Fleexa_Telemetry` | `user_device_id` (`userID#deviceID`) | `timestamp` |
| `Fleexa_Alerts` | `alert_id` (GSIs: `UserAlertsIndex` on `user_id`, `DeviceAlertsIndex` on `user_device_id`) | `timestamp` |
| `Fleexa_Commands` | `command_id` (GSI: `DeviceHistoryIndex`) | `timestamp` |
| `Fleexa_Users` | `user_id` | — |

Every MQTT topic follows `devices/{user_id}/{device_id}/{telemetry|alerts|commands}` (enforced by `internal/validation` on the way in, and by the device's own IoT Policy on the way out). Combined with `api-service` resolving `user_id` strictly from the verified JWT `sub` claim (never from a client-supplied field), this means:
- A device cannot publish under another user's or another device's topic (IoT Policy).
- An ingested message cannot be misattributed to another user even if it arrived on the right topic, because `internal/validation` cross-checks the envelope against the topic.
- A REST client cannot read or command another account's devices, because every handler in `internal/api/handlers` scopes its DynamoDB reads/writes and its outbound command topic to the caller's own `user_id`.

## 6. Push notification credentials

Firebase Cloud Messaging credentials (`FIREBASE_CREDENTIALS`) are injected into the ingestion, `door-watch`, and `ac-timer-watch` Lambdas as an environment variable containing the Firebase service-account JSON (`firebase_credentials_json` in Terraform, marked `sensitive`), rather than a checked-in file. `internal/notifications.NewService` sanitizes and parses this JSON at cold start to initialize the Firebase Admin SDK; pushes are sent only to FCM tokens already associated with the target `user_id` in `Fleexa_Users`, so a notification can never be delivered to the wrong account.

## 7. Secrets and credentials handling

- AWS credentials for local simulator development are supplied via a `.env` file (`devices/.env`, git-ignored) — never committed.
- The Terraform state backend and provider configuration (`backend.tf`, `provider.tf`) and CI both source AWS credentials from GitHub Actions secrets scoped to the `AWS` environment, not from files in the repository.
- Cognito is the sole source of truth for user passwords; the backend never stores or logs a plaintext password.
